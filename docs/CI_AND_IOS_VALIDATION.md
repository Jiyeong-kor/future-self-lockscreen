# CI 운영과 iOS 네이티브 검증

- 작성일: 2026-09-24
- 제품 기준: PRD v1.2
- 목적: 중간 수정마다 main에서 실패를 발생시키던 작업 방식을 교정하고 네이티브 검증을 시작한다.

## 확인한 기존 상태

작업 시작 시 main은 `92a2176eeb1276cfb038f777939219903b21157b`였다. CI 실행 `35896362498`은 성공했다. 직전 코드 커밋의 검사에서는 52개 앱 테스트가 통과했고 린트 경고 17개가 남았다.

과거 실패는 실제 TypeScript 오류, Jest의 의존성 변환 문제, 테스트의 버튼 조회 오류 등을 포함한다. 이후 커밋에서 해결됐다고 해서 당시의 실패가 잘못된 알림이 되는 것은 아니다.

기존 Dependency Audit은 `continue-on-error: true`로 실행됐다. 따라서 일반 CI나 이 보안 작업의 성공 표시만으로 취약점이 없다고 판단할 수 없다. 이번 변경은 이 설정을 제거한다.

## 변경 단위와 알림

변경 파일을 로컬에서 준비하고 관련 파일 전체를 하나의 커밋으로 묶는다. main에 직접 쓰지 않고 작업 브랜치와 PR을 사용한다. PR을 열기 전에 가능한 검사를 실행한다.

CI는 main의 push, main 대상 PR, 명시적인 수동 실행을 처리한다. 작업 브랜치 push만으로 별도 CI를 중복 실행하지 않는다. 같은 PR 또는 브랜치의 오래된 실행은 concurrency로 취소한다. 취소는 실패 해결이 아니며 최신 실행의 결과를 다시 확인한다.

보안 검사와 iOS 빌드는 CI에서 호출하는 재사용 워크플로이다. 독립적인 push/PR 트리거를 중복 등록하지 않는다. 실제 실패를 숨기거나 사용자의 이메일 알림 설정을 변경하지 않는다.

검증 전 main 병합은 하지 않는다. 저장소의 브랜치 보호 설정은 이 코드 변경으로 설정되는 것이 아니다. 작업 시작 시 해당 설정은 꺼져 있었으며, 이번 작업은 저장소 관리 설정을 변경하지 않는다.

## 검사별 의미

| 검사 | 확인 범위 | 확인하지 않는 범위 |
| --- | --- | --- |
| validate | TypeScript, 기존 앱 테스트, 린트, 감사 판정 스크립트 테스트 | iPhone 터치, SQLCipher 런타임, Keychain |
| dependency-audit | 개발 도구를 포함한 npm 의존성 전체, 보고서 유효성, 높은 심각도와 치명적 취약점 | 모든 취약점의 실제 공격 가능성, CocoaPods 보안 전체 |
| ios-build | CocoaPods 설치, JS 번들 생성, 서명 없는 iOS Simulator 빌드 | 실기기 실행, 앱 잠금, DB 암호화와 파일 보호 검증 |

높은 심각도 또는 치명적인 취약점, npm 검사 오류, 시간 초과, 손상된 보고서는 보안 작업을 실패시킨다. 낮은 심각도와 중간 심각도는 원문 보고서 및 작업 요약에 남긴다. 게이트 통과를 무취약점 선언으로 표현하지 않는다.

iOS 관련 파일, npm 의존성, Gemfile, 워크플로가 바뀌면 네이티브 빌드를 실행한다. 비교 기준을 확인할 수 없는 경우에도 빌드를 실행한다. JS만 바뀐 경우 기존 앱 검사는 수행하지만 네이티브 컴파일은 매번 반복하지 않는다. 수동 CI 실행은 네이티브 빌드도 수행한다.

## 앱 전환기 화면 가림 구현

현재 iOS 앱은 AppDelegate와 단일 앱 창을 사용한다. 앱이 비활성화될 때 네이티브 UIView를 동기적으로 올리고, 백그라운드에 들어갈 때 다시 가장 앞에 배치한다. 가림 뷰는 불투명한 시스템 배경색이며 사용자 기록을 담지 않는다. 애니메이션이나 JS 처리를 기다리지 않는다.

앱이 다시 활성화되면 가림 뷰를 제거한다. 기존 입력 내용이나 모달을 지우거나 강제 종료하지 않는다. 접근성 숨김 상태도 원래 값으로 복구한다.

이 기능은 Face ID 앱 잠금, 스크린샷 차단, 화면 녹화 차단, DB 파일 보호 기능이 아니다. 앱 잠금 도입 시에는 활성화만으로 인증 게이트를 제거하지 않도록 통합해야 한다. SceneDelegate나 다중 창을 도입할 때에는 장면별 수명주기 처리가 필요하다.

## 기기 검증 체크리스트

가상 데이터만 사용한다. 아래 항목은 코드 작성 또는 빌드 성공만으로 통과 처리하지 않는다.

- 홈, 기록 목록, 의미 상세, 작성 모달을 연 상태에서 앱 전환기 미리보기에 개인 문장이 남지 않는지 확인한다.
- 입력 중 앱 전환, 제어 센터, 시스템 권한 팝업을 거친 뒤 입력과 화면이 유지되는지 확인한다.
- 키보드 표시, 가로·세로 전환, 다크 모드, VoiceOver를 확인한다.
- 비활성화와 활성화를 반복해 가림 뷰가 겹치거나 영구적으로 남지 않는지 확인한다.
- 앱 잠금과 이 화면 가림을 혼동하지 않는지 확인한다.
- SQLCipher 사용 여부, 재실행 후 기록 유지, 키 접근 실패 처리, DB/WAL/SHM의 파일 보호와 백업 제외를 별도로 검증한다.

## 검증 기록

이번 변경의 감사 판정 스크립트 테스트는 로컬 Node 22에서 13개를 통과했다. null 또는 기본형 JSON과 알 수 없는 보고서 버전도 검증한다. Swift 파일은 구문 분석을 실행했으나 Linux의 구문 분석은 UIKit 타입 검사나 iOS 빌드가 아니다. 최종 PR 검사는 GitHub Actions의 해당 커밋 결과를 기준으로 판단한다.

### 확인한 실행

- 최초 PR 커밋 `2fc41f4a47303e63fbe3e385d7414bea8a2d1ab5`의 [CI 실행 35897954743](https://github.com/Jiyeong-kor/future-self-lockscreen/actions/runs/35897954743)에서 앱 검사와 iOS Simulator 빌드가 통과했다. CocoaPods 설치, JavaScript 번들 생성, UIKit을 포함한 컴파일·링크까지 수행했다. 이때 의존성 검사는 기존 높은 심각도 항목 때문에 실패했다.
- [의존성 수정안 검증 실행 35899427313](https://github.com/Jiyeong-kor/future-self-lockscreen/actions/runs/35899427313)에서는 새 lockfile로 앱 검사와 npm audit을 통과했다. npm 보고는 모든 심각도 0개였다. 보안 예외를 추가해서 통과시킨 결과가 아니다.
- 최종 PR 커밋에 반영한 lockfile과 감사 판정 스크립트는 PR에서 다시 검사한다. 위 첫 iOS 빌드 결과를 새 lockfile의 네이티브 빌드 결과로 대체하지 않는다.

이 문서는 네이티브 검증 기반과 화면 가림 코드를 추가한 상태를 설명한다. 실기기 개인정보 보호 검증 완료를 선언하지 않는다.
